Two Calibration Tracks

How the same speed-measurement engine is bootstrapped two different ways — Depth Pro for oblique cameras, closed-form geometry for overhead (drone) views — and why the two must not be swapped.

1. One engine, two bootstraps

Both tracks feed the identical per-frame runtime. A vehicle's ground position is an exact ray/plane intersection, its speed a least-squares fit over 0.6 s, and a reading is withheld when it falls below the geometric noise floor. None of that differs between the tracks. What differs is only how the five calibration numbers — focal length f, principal point (cx,cy), ground normal n, and camera height h — are obtained.

Track A — Depth Pro (oblique)

Pole, overpass, CCTV. The ground plane is tilted and unknown, so it is measured from a monocular depth map.

detector → road mask → Depth Pro (2 frames) →
focal from FOV head · normal from RANSAC plane →
height from car width → calib.json + depth map

Track B — Overhead (drone / nadir)

Camera points straight down. The plane is perpendicular to the optical axis, so its geometry is known — no depth model runs at all.

normal fixed at [0,0,−1] · focal set arbitrarily →
height from car width (aerial detector) →
calib.json (no depth map made)

The one thing neither track trusts a network for: scale. Camera height in both tracks comes from measuring apparent car width against a 1.83 m physical constant, never from a depth model's absolute output. Depth Pro is used for the road's shape (Track A), not its range.

2. Track A — Depth Pro for oblique cameras

2.1 Why a depth model at all

On a tilted view, metres-per-pixel varies across the frame: a car near the horizon covers several times more ground per pixel than one in the foreground. The single constant the original system used is only valid for a fronto-parallel plane. To recover the true plane, one needs its orientation and the camera's focal length — and a monocular metric-depth model supplies both.

2.2 What is taken from Depth Pro, and what is not

  • Focal length ← the FOV head. This is the sole reason the large model is used. An attempt to recover focal from planarity alone failed structurally (as f→∞ every point collapses onto a line, which is trivially planar, so any such search runs away) — measured 5760 px ceiling and 7–8° tilt against a 23.75° vanishing-point truth.
  • Plane orientation ← RANSAC on the point cloud, keeping only the unit normal. A normalized vector is invariant to a wrong global depth scale, which matters because Depth Pro's absolute scale is out of distribution on aerial or unusual views.
  • Absolute depth is discarded. The depth map is used to fit orientation and to render the overlay; it never touches the runtime measurement.

2.3 Geometry

ray:          d(u,v) = [ (u−cx)/f , (v−cy)/f , 1 ]ᵀ
intersection: t = −(h − z) / (n · d)          valid iff  n·d < 0
world:        X = [ P·r̂ , P·ŵ , P·n + h ]ᵀ    distance D = ‖P‖
depth profile: D(v) ≈ h·f / (v − v_horizon)
Why tilt error is catastrophic here. D diverges at the horizon, so a small error in n shifts v_horizon and rescales the entire far field. A horizon mistakenly placed above the frame compressed motorway traffic to 12–16 km/h until the input resolution was fixed.

2.4 Resource discipline

  • The detector is freed before Depth Pro loads — holding both on an Apple-Silicon unified-memory machine exhausts it.
  • fp16 on MPS: focal matched a CPU fp32 reference to 0.06% with identical depth percentiles, at 5× the speed and half the memory.
  • Input is fixed at 1536×1536 (not reducible), so cost is ~7 GB regardless of source resolution.

3. Track B — closed-form overhead (drone) view

3.1 Depth is constant — nothing to estimate

For a camera pointing straight down, the normal is exactly [0,0,−1], so n·d = −1 identically and the intersection collapses:

t = −(h−z)/(−1) = h − z            ← independent of (u,v)
P = (h−z) · [ (u−cx)/f , (v−cy)/f , 1 ]ᵀ

The Z-component of every ground point is exactly h−z: depth is the same everywhere in frame. Verified on real footage — 65.20 m at the centre, 65.20 m at the corners; only the slant distance ‖P‖ varies (to 70.94 m). A depth network would be estimating a constant.

3.2 Running a depth model here would be actively harmful

Plane tilt is recovered from the depth gradient across the frame, which is ~zero looking straight down. A fit therefore has no signal and merely converts the model's own error into tilt that is not there — amplified by f/(W/2) ≈ 1.67×, so a 3% depth error becomes ~3° of false tilt. The correct move is to skip it entirely.

3.3 Focal length is unidentifiable — and that is fine

x = (h−z)(u−cx)/f      y = (h−z)(v−cy)/f

h and f appear only as the ratio h/f. So any focal gives identical ground positions and speeds; the code fixes f = W_img arbitrarily and solves h from car width to match the true ratio. Only the reported slant distance depends on the split, which a known altitude resolves:

f′ = f · H_true / h ,  h′ = H_true   ⟹   h′/f′ = h/f   (positions unchanged)
This is why the original one-constant model worked overhead. A single METERS_PER_PIXEL = h/f is the exact correct model for a nadir view — and only for a nadir view. The original code was not wrong for drones; it was wrong to assume every camera was a drone.

3.4 A different detector, not just different geometry

A COCO-trained model barely recognises a car seen from directly above — different aspect, no visible face or wheels. Measured on the drone clip: yolo11s found 0 vehicles per frame at conf 0.25 and 1–2 at conf 0.10, where the aerial-trained visDrone found 23–28. Track B therefore switches the detector as well as the calibration.

4. Shared: scale, speed, and the honesty gate

4.1 Scale — the physical anchor (both tracks)

w₁ = W / (h − z_b)      ⟹      h = W / w₁ + z_b        (W = 1.83 m, z_b = 0.75 m)
  • The z_b term corrects for the box's lateral extremities sitting on the car body, not the road; omitting it cost a 16% scale error.
  • 25th percentile, not median. The axis-aligned box spans L·|cos φ| + W·|sin φ| ≥ W, so length contamination can only inflate the width — a one-sided error. Scored against lane markings: min +140%, p5 +12%, p25 +2%, median −6%.

4.2 Speed and the noise floor (both tracks)

speed = 3.6·√(v_x² + v_y²)   from an OLS fit over ~0.6 s
σ_v   = 3.6 · 2·JITTER_FRAC·W·D / (h·T)      (linear in distance, measured d^1.00)

A reading must clear 2σ to be claimed; below that it is UNRELIABLE rather than a guessed number. Three deliberately distinct output states — N km/h (measured), 0.0 (stopped) (valid), and UNRELIABLE (no claim) — keep a parked car and a tracker glitch tellable apart.

5. The failure mode the two tracks share

Both tracks are exact once calibrated; the weak layer is the inputs. Every silent failure observed in development came from an unvalidated assumption, not from the geometry:
